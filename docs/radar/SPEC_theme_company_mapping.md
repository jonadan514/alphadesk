---

## 0. 왜 이 작업이 가장 중요한가

테마 보드의 세 축이 전부 "테마 소속 기업"을 전제로 계산된다.

- 실적 축 = 소속 기업 중 매출 개선 비율
- 주가 축 = 소속 기업 4주 수익률 중앙값

**매핑이 부실하면 그 위의 모든 숫자가 무의미해진다.** 엉뚱한 기업이 섞이면 실적 축이 그 기업 사정을 반영하고, 핵심 기업이 빠지면 테마가 움직여도 감지가 안 된다.

동시에 이 작업은 **자동으로 완벽하게 만들 수 없다.** 최종 목록은 사람이 한 번 훑어야 한다. 그 전제로 설계한다.

---

## 1. LLM의 역할 한계 — 반드시 지킬 것

이 파이프라인에서 LLM은 **두 가지 일만** 한다.

| 허용 | 금지 |
|---|---|
| 어떤 기업이 이 테마에 속하는지 후보를 던진다 | **재무 수치를 답하게 한다** |
| 왜 속하는지 한 줄 근거를 쓴다 | 매출·성장률·마진을 조회하게 한다 |
| | 실적이 좋아지고 있는지 판단하게 한다 |

**숫자는 오직 `fundamentals_cache`(DART / yfinance)에서만 나온다.** LLM에게 재무를 물으면 학습 시점 숫자를 현재처럼 답하거나, 연결/별도를 혼동하거나, 단위를 틀린다. 그리고 틀렸다는 표시 없이 맞는 답과 같은 어조로 답한다.

후보 생성은 틀려도 안전하다 — 뒤에서 코드가 거른다. 숫자는 틀리면 그대로 화면에 나간다.

## 2. 매핑 방식 — 두 경로를 합집합으로

### 경로 A: 유니버스 제약 선택 (주 경로)

유니버스 목록을 **LLM에게 직접 주고 그 안에서 고르게 한다.**

```
입력: [AAPL - Apple Inc, NVDA - NVIDIA Corp, ... 200개]
질문: 위 목록에서 "데이터센터 전력" 테마에 해당하는 기업을 고르시오
```

- 유니버스를 200개씩 청크로 나눠 반복 호출
- **환각 티커가 원천적으로 발생하지 않는다** — 목록에 없는 건 못 고른다
- 미국 900개 기준 테마당 5회 호출

### 경로 B: 자유 생성 (보조 경로)

목록 없이 "이 테마에 해당하는 상장기업"을 묻는다. 유니버스에 없는 기업(중형주 미편입, 최근 상장)을 잡기 위함이며, **결과는 반드시 §4 검증을 통과해야 한다.**

### 합집합 후 중복 제거

경로 A와 B 결과를 합치고 티커 기준 중복 제거. 두 경로 모두에서 나온 기업은 `confidence: high`로 표시.

---

## 3. 프롬프트 설계

### 3.1 핵심 원칙 — "이 테마 회사"가 아니라 "가치사슬 위치"를 묻는다

**나쁜 질문**: "피지컬 AI 기업을 알려줘"
→ LLM이 뭐든 갖다 붙인다. AI를 언급한 적 있는 모든 회사가 나온다.

**좋은 질문**: 테마의 가치사슬 단계를 명시하고, 각 단계에 해당하는 기업을 고르게 한다.

```
"피지컬 AI" 테마는 다음 가치사슬로 구성된다:
  (1) 센서: 머신비전 카메라, 라이다, 힘/토크 센서
  (2) 엣지 연산: 로봇·기계에 탑재되는 추론 반도체 및 모듈
  (3) 구동부: 액추에이터, 감속기, 서보모터
  (4) 제어 소프트웨어: 로봇 파운데이션 모델, 모션 제어
  (5) 채택 설비: 위 기술을 탑재해 판매하는 장비·설비 업체

각 기업에 대해 어느 단계에 해당하는지 명시하시오.
어느 단계에도 명확히 속하지 않으면 포함하지 마시오.
```

`themes.yaml`의 `note` 필드에 이 가치사슬 정의를 넣어두고 프롬프트에 주입한다.

### 3.2 반드시 받아야 할 필드

```json
{
  "ticker": "005930.KS",
  "name": "삼성전자",
  "market": "KR",
  "value_chain_stage": "엣지 연산",
  "evidence": "차량·로봇용 이미지센서 및 AP를 생산해 공급",
  "linkage": "partial"
}
```

- **`ticker` 필수.** 회사명만 받으면 매칭이 지옥이다. 표기 흔들림, 동명이인, 계열사 혼동이 발생한다.
- **`evidence` 필수, 그리고 구체적일 것.** "AI 관련 사업 영위" 같은 뭉뚱그린 근거는 LLM이 대충 넣었다는 신호다. **구체적 제품명이나 사업부가 없으면 §4에서 탈락시킨다.**
- **`linkage`**: `direct`(주력 사업) / `partial`(일부 사업부) / `peripheral`(간접 노출). 화면에 표시하고, 실적 축 계산에서는 `peripheral` 제외를 옵션으로 둔다.

### 3.3 웹 검색 허용

LLM 내부 지식만 쓰면 학습 시점에 갇힌다. 웹 검색을 붙여 최근 편입 기업이나 신규 사업 진출을 잡는다.

**단, 검색을 붙여도 숫자는 여전히 신뢰하지 않는다.** 기사의 수치를 잘못 옮기는 것은 검색 유무와 무관하게 발생한다.

### 3.4 2차 비판 패스 (권장)

1차 목록을 만든 뒤, **같은 LLM에게 그 목록을 비판하게 한다.**

```
아래는 "OO 테마" 후보 목록이다.
이 중 해당 테마 관련 매출이 전체의 10% 미만일 것으로 보이는 기업,
또는 근거가 약해 제외해야 할 기업을 지적하시오.
```

호출 한 번으로 과포함을 상당히 줄일 수 있다. 결과는 삭제가 아니라 `flagged: true` 표시로 남기고, 사람 검토 때 우선 확인 대상으로 올린다.

## 4. 코드 검증 파이프라인

LLM이 뱉은 후보는 **전부** 아래를 통과해야 한다. 통과 못 하면 조용히 버린다.

```
1. 티커 실재 확인
   → 유니버스 목록(S&P 500/400, KRX)에 존재하는가
   → 없으면 폐기. 로그에 남김 (환각 비율 측정용)

2. 시가총액 하한
   → 미국 $2B+, 한국 2000억원+
   → 유니버스 기준과 동일하게 적용

3. 재무 데이터 존재 확인
   → fundamentals_cache 에 해당 티커 데이터가 있는가
   → 없으면 'insufficient_data' 로 분류 (탈락과 구분)

4. evidence 품질 검사
   → 길이 15자 미만 폐기
   → 금칙어 패턴("관련 사업", "수혜 예상", "테마주") 포함 시 flagged

5. 중복 제거
   → 티커 기준. 여러 테마 소속은 허용 (테마별로 각각 행 생성)
```

**1번 폐기율을 반드시 로그에 남긴다.** 경로 B(자유 생성)의 환각률이 이 숫자로 드러난다. 30%를 넘으면 경로 B를 축소하거나 프롬프트를 손봐야 한다.

## 5. 스키마

```sql
CREATE TABLE IF NOT EXISTS theme_members (
  theme_id     TEXT NOT NULL,
  ticker       TEXT NOT NULL,
  market       TEXT NOT NULL,           -- 'US' | 'KR'
  stage        TEXT,                    -- 가치사슬 단계
  evidence     TEXT,                    -- 왜 이 테마인가 (한 줄)
  linkage      TEXT,                    -- 'direct' | 'partial' | 'peripheral'
  confidence   TEXT,                    -- 'high' | 'normal'
  flagged      INTEGER DEFAULT 0,       -- 2차 비판 패스에서 지적됨
  approved     INTEGER DEFAULT 0,       -- 사람 검토 통과 여부
  run_id       TEXT NOT NULL,           -- 어느 매핑 실행에서 나왔나
  created_at   TEXT NOT NULL,
  PRIMARY KEY (theme_id, ticker, run_id)
);

CREATE TABLE IF NOT EXISTS mapping_runs (
  run_id       TEXT PRIMARY KEY,
  started_at   TEXT,
  finished_at  TEXT,
  model        TEXT,                    -- 어떤 모델로 돌렸나
  prompt_ver   TEXT,                    -- 프롬프트 버전
  stats        TEXT                     -- JSON: 테마별 후보수/폐기수/환각률
);
```

**`run_id`로 실행을 통째로 보존한다.** 덮어쓰지 않는다. 이유:

- 프롬프트나 모델을 바꿨을 때 결과가 어떻게 달라졌는지 비교할 수 있다
- **"이번 분기에 테마에 새로 들어온 기업"을 diff로 뽑을 수 있다.** 이게 그 자체로 읽을거리다
- 과거 테마 지표를 재계산할 때 그 시점 구성원으로 계산해야 정확하다

현재 유효 매핑은 최신 `run_id` + `approved = 1` 로 조회한다.

## 6. 실행 주기

**분기 1회.** 주간 배치에 넣지 않는다.

이유: 테마 목록이 고정이므로 소속 기업도 거의 고정이다. 매주 LLM을 돌리면 비용만 들고 **결과가 매번 미묘하게 달라져서 추이 비교가 깨진다.**

예외적으로 수동 재실행이 필요한 경우:
- `themes.yaml`에 테마를 추가했을 때 (해당 테마만)
- 대형 상장/합병이 있었을 때

워크플로: `.github/workflows/theme-mapping.yml`, `workflow_dispatch` 전용, 입력으로 `theme_id`(선택, 비우면 전체) 받음.

## 7. 사람 검토 단계 — 첫 실행은 필수

첫 `run_id`의 결과는 **`approved = 0` 상태로 저장되고, 승인 전까지 테마 보드에 반영되지 않는다.**

검토용 화면 또는 CSV 출력을 제공한다:

```
theme_id, ticker, name, stage, linkage, evidence, flagged
```

검토 방법:
1. `flagged = 1` 항목 먼저 확인
2. 테마별 목록을 훑으며 명백히 이상한 것 제외
3. 잘 아는 테마 2~3개를 골라 **빠진 기업이 없는지** 확인 (과포함보다 누락이 발견하기 어렵다)

2회차부터는 **직전 run과의 diff만 검토**하면 된다. 대부분 변화가 없을 것이다.

## 8. 완료 조건

| 항목 | 기준 |
|---|---|
| 테마별 기업 수 | **10~30개 범위** |
| 3개 이하인 테마 | 상위 테마에 흡수하거나 `themes.yaml`에서 제외 |
| 50개 이상인 테마 | 가치사슬 단계로 분리 검토 |
| 환각 폐기율 (경로 B) | 30% 미만 |
| 사람 검토 | 첫 run 전체 승인 완료 |

**테마별 기업 수 분포를 반드시 표로 출력한다.** 이 숫자를 보고 `themes.yaml`을 조정하는 것이 이 단계의 실질적 산출물이다.

### 예상되는 조정 대상 (첫 실행 후 확인)

- `datacenter_cooling`, `cable_wire`, `specialty_gas` — 너무 좁을 가능성
- `ai_semiconductor`, `battery` — 50개 넘을 가능성
- `power_grid` / `datacenter_power` / `cable_wire` — 구성원 중복률 확인. 70% 이상 겹치면 통합
- `physical_ai` / `factory_automation` / `humanoid_robot` — 동일하게 중복률 확인

## 9. 알려진 실패 모드

**과포함이 기본값이다.** LLM은 "관련 없음"보다 "약간 관련 있음"을 선호한다. 대형주는 사업이 많아서 거의 모든 테마에 걸릴 수 있다(삼성전자, 애플 등). `linkage: peripheral`이 과반이면 프롬프트가 느슨한 것이다.

**누락은 눈에 안 띈다.** 목록에 없는 기업은 화면에도 없어서 문제를 알아채기 어렵다. §7의 "빠진 기업 확인"이 이걸 잡는 유일한 장치다.

**한국 기업 인식률이 낮다.** LLM이 한국 중소형주를 잘 모른다. 경로 A(유니버스 제약 선택)가 특히 중요하다 — 목록을 주면 알아본다. 자유 생성만으로는 대형주만 나온다.

**테마 편중.** 뉴스가 많은 테마일수록 LLM이 기업을 많이 안다. 조용한 테마(`petrochemical`, `rail` 등)는 목록이 얇게 나올 수 있는데, 이건 그 테마에 기업이 적어서가 아니라 **LLM이 덜 알아서**다. 경로 A로 보완된다.

## 10. 이후 단계와의 연결

이 매핑이 끝나면 세 축 계산은 상대적으로 단순하다:

```
뉴스 축  = themes.yaml 키워드로 집계     (매핑 불필요)
실적 축  = theme_members × fundamentals_cache 조인
주가 축  = theme_members × 주가 데이터 조인
```

**실적 축·주가 축 계산 시 `linkage` 필터를 옵션으로 노출한다.** `peripheral` 포함 여부에 따라 결과가 크게 달라질 수 있으므로, 기본값은 `direct + partial`로 두고 비교 가능하게 한다.
