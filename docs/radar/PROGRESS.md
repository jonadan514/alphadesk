  재시도까지 실패하면 회로차단기가 켜져서, 남은 종목은 재시도 없이 바로

  "이번 주 갱신 시도 중 (라이브 성공+캐시 폴백)/전체 시도"로 정의함.

**검증**

## 2026-08-31 — §3 실전 배포 후 발견된 성능 문제 + 최적화

**무엇을 구현했는지**
- `get_cached_financials_bulk()`(`fundamentals_cache.py`) 추가 — 여러 종목을
  200개씩 청크로 묶어 `IN (...)` 쿼리 한 번에 조회. `collect_universe()`가
  캐시 대상 전체를 루프 시작 전에 한꺼번에 읽어두도록 변경.
- 기존 단일 조회 로직은 `_reconstruct()` 공용 헬퍼로 뽑아 `get_cached_financials()`
  (단일)와 `get_cached_financials_bulk()`(벌크)가 공유.

**왜 필요했는지 (§3 배포 후 실측)**
- §3 배포 직후 첫 프로덕션 실행: 실행 시간이 기존 13~15분 → **20분 51초로
  오히려 증가.** 로그를 시간대별로 뜯어보니 캐시로 읽는 종목(약 530개)이
  종목마다 Turso에 개별 HTTP 조회(2회씩, fundamentals_cache + fetch_status)를
  했고, 이게 종목당 약 0.8초씩 쌓여 약 7분이 새로 추가된 것으로 확인됨.
  로컬 테스트 땐 로컬 SQLite라 이 비용이 0에 가까워서 못 봤음 — **Turso
  왕복 비용을 실측 없이 로컬로만 검증한 게 이번 세션의 리뷰 허점.**
  (워치리스트 후보 수는 164개로 이전과 비슷해 정확성 자체는 문제없었음)
- 최적화로 종목 수(최대 ~530)와 무관하게 쿼리 횟수가 고정(청크당 2회,
  200개 기준 최대 3청크 = 6회)으로 줄어듦.

**최적화 배포 후 프로덕션 재실행 결과 (2026-08-31)**
- 실행 시간 **20분 51초 → 5분 5초** (§3 적용 전 13~15분보다도 빠름).
  재무 데이터 수집 자체는 2분 47초(이전 15분 39초 대비 82% 감소) — 종목
  150번째 이후로는 캐시 조회가 사실상 즉시 끝남(벌크 조회 정상 작동 확인).
  이전 실행에 있었던 150~200구간 이상 지연도 재현 안 됨.
- 결과: 유니버스 586종목 → 통과 166(US 154 + KR 12) / 탈락 420(71.7%).
  이전(161~164개)과 비슷한 규모 — 정확성 유지 확인.
