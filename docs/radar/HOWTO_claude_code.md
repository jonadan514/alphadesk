# 클로드 코드 이관 가이드

**작성일**: 2026-08-27

---

## 1. 파일 배치

저장소에 `docs/radar/` 폴더를 만들고 다섯 개를 넣는다.

```
alphadesk/
├── docs/
│   └── radar/
│       ├── MASTER_PLAN_research_radar.md      ← 최상위 기준
│       ├── SPEC_fundamentals_cache.md         ← Phase 0
│       ├── SPEC_theme_company_mapping.md      ← Phase A-2
│       ├── SPEC_phase_a_signals.md            ← Phase A-3~6
│       └── themes.yaml                        ← 참조용 사본
└── config/
    └── themes.yaml                            ← 실제 코드가 읽는 파일
```

`themes.yaml`은 두 군데 두지 말고 `config/themes.yaml` 하나만 두는 게 낫다. docs에는 링크만 적어둔다.

**먼저 커밋부터 한다.** 문서를 커밋해두면 클로드 코드가 언제든 다시 읽을 수 있고, 대화가 길어져 앞부분을 잊어도 파일이 남는다.

## 2. CLAUDE.md에 넣을 것

저장소 루트의 `CLAUDE.md`(없으면 생성)에 아래를 추가한다. 클로드 코드가 매 세션 자동으로 읽는 파일이다.

```markdown
## 진행 중인 전환: 리서치 레이더

이 저장소는 종목 스크리너에서 테마 기반 주간 리서치 레이더로
전환 중이다. 작업 전 반드시 `docs/radar/MASTER_PLAN_research_radar.md`를
읽을 것.

### 반드시 지킬 원칙
1. 단일 종합 점수·등급을 만들지 않는다. 세 축을 각각 표시한다.
2. LLM은 재무 수치를 생성하지 않는다. 숫자는 fundamentals_cache에서만 나온다.
3. 트랩 필터 기준값(F-Score 6, ROE 미국 12%/한국 8%, 이자보상 3배, 부채비율 150%)을
   임의로 바꾸지 않는다.
4. 판정은 통과/탈락/데이터부족 3분류. 계산 불가를 탈락으로 처리하지 않는다.
5. 이력 테이블은 덮어쓰지 않는다.

### 문서
- MASTER_PLAN_research_radar.md — 전체 계획, 원칙, 로드맵
- SPEC_fundamentals_cache.md — Phase 0
- SPEC_theme_company_mapping.md — Phase A-2
- SPEC_phase_a_signals.md — Phase A-3~6
```

## 3. 작업 순서

**한 세션에 한 단계만.** 명세 하나를 통째로 넘기면 얕은 결과가 나온다.

| 순서 | 작업 | 명세 |
|---:|---|---|
| 0 | **기능 제거** (포트폴리오·게이트·`/workflow`·`/risk`) | 마스터 §7 |
| 1 | 테이블 2개 생성 | 캐시 §2 |
| 2 | 백필 워크플로 | 캐시 §5 |
| 3 | 백필 수동 실행 (2~3일) | — |
| 4 | 필터를 캐시 기반으로 | 캐시 §4 |
| 5 | 갱신 예산제 | 캐시 §3 |
| 6 | 실패 내성 | 캐시 §6 |
| 7 | 시가총액 배치화 | 캐시 §7 |
| 8 | 테마 매핑 테이블 + 워크플로 | 매핑 전체 |
| 9 | 매핑 실행 + 사람 검토 | 매핑 §7 |
| 10 | 뉴스 수집 + 백필 8주 | Phase A §2 |
| 11 | 실적 축 | Phase A §3 |
| 12 | 주가 축 | Phase A §4 |
| 13 | 라벨 + 화면 | Phase A §5~6 |

**0번을 맨 앞에 두는 이유**: 지울 코드를 놔둔 채 캐시 작업을 하면, 없어질 기능까지 캐시에 맞춰 고치게 된다. 헛일이다.

**단, 0번은 지우기 전에 조사부터 시킨다.** 아래 §4-1 참조.

**3번과 9번은 사람이 하는 일이다.** 클로드 코드가 아니라 네가 직접 워크플로를 돌리고 결과를 확인한다.

## 3-1. 0번(기능 제거) 지시문

제거는 되돌리기 어려우니 두 세션으로 나눈다.

**세션 1 — 조사만**

```
docs/radar/MASTER_PLAN_research_radar.md 의 §7 을 읽어줘.

거기 적힌 제거 대상들을 실제로 지우기 전에, 먼저 조사만 해줘.
코드는 아직 건드리지 마.

1. 각 대상이 어느 파일·어느 워크플로에 걸쳐 있는지
2. 지웠을 때 같이 깨지는 것이 있는지 (다른 기능이 참조하고 있는지)
3. 거시지표(금리·환율·유가 등) 수집 코드 중
   나중에 레짐 모듈에서 재사용할 수 있는 것은 무엇인지
4. performance-tracking.yml 이 포트폴리오에 의존하는지,
   아니면 watchlist_candidate_history 만 쓰는지

조사 결과를 docs/radar/REMOVAL_PLAN.md 로 정리해줘.
```

**4번이 특히 중요하다.** `performance-tracking`은 필터가 맞는지 검증하는 유일한 장치다. 포트폴리오에 딸려 지워지면 안 된다.

**세션 2 — 실행**

```
REMOVAL_PLAN.md 대로 제거를 진행해줘.

단 아래는 남긴다:
- performance-tracking.yml
- watchlist_candidates, watchlist_candidate_history 테이블
- 거시지표 수집 코드 (레짐 모듈 재사용분)
- /sector (주가 축에서 쓸 예정)

DB 테이블은 DROP 하지 말고 코드 참조만 끊어줘.
데이터는 남겨두고, 나중에 확실해지면 그때 지운다.
```

## 4. 지시문 템플릿

각 단계마다 이 형태로 시작한다.

```
docs/radar/MASTER_PLAN_research_radar.md 와
docs/radar/SPEC_fundamentals_cache.md 를 읽어줘.

오늘은 §2 스키마와 §5 백필 워크플로만 구현한다.
§3 예산제, §4 필터 변경, §6 실패 내성은 다음 세션에서 할 거니까
지금은 건드리지 마.

구현 전에 먼저:
1. 현재 코드에서 재무 데이터를 어디서 어떻게 받아오는지 파악해서 설명해줘
2. 그 다음 어떻게 바꿀 건지 계획을 말해줘
3. 내가 확인하면 그때 코드를 써

바로 코드부터 쓰지 마.
```

**"바로 코드부터 쓰지 마"가 중요하다.** 비개발자 입장에서 코드가 먼저 나오면 맞는지 판단할 수가 없다. 계획을 먼저 받아서 읽고 승인하는 순서가 안전하다.

## 5. 세션 마무리 지시

각 세션 끝에:

```
오늘 한 작업을 요약해서 docs/radar/PROGRESS.md 에 추가해줘.
- 무엇을 구현했는지
- 명세와 다르게 구현한 게 있으면 무엇을 왜
- 다음 세션에서 이어서 할 것
- 확인이 필요한 미결 사항
```

**"명세와 다르게 구현한 것"을 꼭 물어라.** 실제 코드를 보면 명세대로 안 되는 경우가 반드시 나오는데, 그걸 기록 안 하면 나중에 문서와 코드가 조용히 어긋난다.

## 6. 검증을 요구할 것

비개발자가 코드를 읽고 맞는지 판단하기는 어렵다. 대신 **결과를 확인할 수 있는 형태로 만들어달라고** 요구한다.

각 단계마다:

```
이게 제대로 됐는지 내가 확인할 수 있는 방법을 알려줘.
가능하면 결과를 출력하는 명령어나 워크플로를 같이 만들어줘.
```

특히 중요한 검증 지점:

| 단계 | 확인 방법 |
|---|---|
| 4 (필터 캐시화) | **캐시 전후 통과 종목 목록이 동일한가** — 다르면 잘못된 것 |
| 9 (매핑) | 테마별 기업 수 표. 10~30개 범위인가 |
| 10 (뉴스) | 중복 제거 전후 건수. 제거율이 이상하지 않은가 |
| 11 (실적) | `insufficient` 비율. 40% 넘는 테마가 몇 개인가 |
| 13 (화면) | 라벨 붙은 테마가 주당 3~10개인가 |

## 7. 흔들리기 쉬운 지점

작업하다 보면 클로드 코드가 "좋은 의도로" 다음을 제안할 수 있다. **전부 거절해야 한다.**

- **"종합 점수를 만들면 정렬이 편할 텐데요"** → 원칙 1 위반. 이미 한 번 지웠다.
- **"LLM으로 재무 데이터를 요약하면 빠릅니다"** → 원칙 2 위반.
- **"데이터 없는 종목은 그냥 제외하죠"** → 원칙 4 위반. `데이터부족`으로 분류해야 한다.
- **"필터가 너무 빡빡하니 기준을 낮출까요"** → 이번 작업 범위 아님. 별도 결정.
- **"기존 테이블 구조를 정리하면서 가겠습니다"** → 이력 테이블은 건드리지 않는다.

CLAUDE.md에 원칙을 박아두는 이유가 이거다. 세션이 길어지면 잊어버린다.
