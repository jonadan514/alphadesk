## 0. 배경 (왜 하는가)

2026-08-25 `Weekly Market Analysis #2`(스케줄 실행)가 `yfinance.exceptions.YFRateLimitError`로 실패했다. 스택 트레이스상 실패 지점은 `_get_crumb_basic` — 특정 종목 데이터 조회가 아니라 **야후 세션 인증(쿠키/crumb) 발급 단계**다. 즉 그 시점엔 어떤 종목도 조회할 수 없는 상태였다.

이 실패로 그 주 장기 포트폴리오(1y/3y) 매수가 실행되지 않았다.

**근본 원인 진단**: GitHub Actions 러너는 IP 풀을 다수 사용자가 공유한다. 같은 IP에서 다른 사용자가 야후를 과하게 호출하면 이쪽 코드가 아무리 얌전해도 차단된다. 한국 유니버스에서 pykrx가 4주 연속 실패한 것(KRX의 클라우드 IP 차단 추정)과 동일한 뿌리로 본다.

**핵심 관찰**: 트랩 필터(§4 항목 6개 — Piotroski, 이자보상배율, 부채비율, OCF, 매출/순이익 추이, ROE)는 **전부 재무제표 기반이며 주가가 들어가는 항목이 하나도 없다.** 재무제표는 분기(약 13주)마다 바뀌는데 현재는 매주 573종목 전체를 다시 받고 있다. 호출의 대부분이 지난주와 동일한 답을 받기 위해 소모된다.

## 2. 스키마

Turso(libSQL/SQLite) 기준. 날짜·시각은 ISO8601 문자열로 저장한다.

### 2.1 `fundamentals_cache`

```sql
CREATE TABLE IF NOT EXISTS fundamentals_cache (
  ticker      TEXT NOT NULL,
  market      TEXT NOT NULL,              -- 'US' | 'KR'
  statement   TEXT NOT NULL,              -- 'income' | 'balance' | 'cashflow'
  period_end  TEXT NOT NULL,              -- 회계기간 종료일 'YYYY-MM-DD'
  data        TEXT NOT NULL,              -- 해당 기간 재무 항목 JSON
  fetched_at  TEXT NOT NULL,              -- 이 값을 받아온 시각
  PRIMARY KEY (ticker, statement, period_end)
);

CREATE INDEX IF NOT EXISTS idx_fund_ticker ON fundamentals_cache(ticker);
```

**중요**: 종목당 JSON 한 덩어리로 뭉치지 말고 **회계기간(period_end)별로 행을 나눈다.** 새 분기가 나오면 행이 하나 추가될 뿐 과거 행은 건드리지 않는다.

**과거 행은 절대 덮어쓰지 않는다.** 기업이 과거 재무제표를 수정공시하면 야후가 주는 숫자가 바뀌는데, 이를 덮어쓰면 "우리가 그때 무엇을 보고 통과시켰는지"를 되짚을 수 없게 된다. 같은 `(ticker, statement, period_end)`에 다른 값이 오면 기존 행 유지 + 로그만 남긴다.

### 2.2 `fetch_status`

```sql
CREATE TABLE IF NOT EXISTS fetch_status (
  ticker           TEXT PRIMARY KEY,
  market           TEXT NOT NULL,
  last_attempt_at  TEXT,
  last_success_at  TEXT,
  status           TEXT,                  -- 'ok' | 'rate_limited' | 'no_data'
  fail_count       INTEGER DEFAULT 0
);
```

`status` 값의 의미를 반드시 구분할 것:

| 값 | 의미 | 후속 동작 |
|---|---|---|
| `ok` | 정상 수집 | 예산 순번대로 갱신 |
| `rate_limited` | 야후가 막음 (데이터는 있을 수 있음) | 다음 실행에서 우선 재시도 |
| `no_data` | 야후에 데이터 자체가 없음 | 재시도 빈도 낮춤 (예: 90일에 1회) |

`no_data`를 구분하지 않으면 영원히 존재하지 않는 데이터를 매주 재시도하며 호출을 낭비한다.

## 3. 갱신 규칙 — TTL 금지, 예산제

### 하지 말 것
`fetched_at`이 90일 지나면 갱신하는 단순 TTL 방식. 초기 백필에서 573종목을 한꺼번에 채우면 **90일 뒤 전부 동시에 만료되어 그 주에 573건을 몰아 호출한다.** 지금과 같은 실패가 분기마다 반복된다.

### 할 것
```
매주 실행 시:
  1. fetch_status에서 status='rate_limited' 종목을 우선 큐에 넣는다
  2. 나머지를 last_success_at 오래된 순(NULL 먼저)으로 정렬해 채운다
  3. 상위 REFRESH_BUDGET 개만 야후에서 갱신한다
  4. 나머지 전 종목은 캐시된 값을 그대로 사용한다
```

- `REFRESH_BUDGET`은 환경변수로 노출 (기본값 **60**)
- 573종목 기준 약 10주에 한 바퀴 → 재무제표 갱신 주기(13주)보다 짧으므로 충분
- 호출량이 데이터 상태와 무관하게 항상 일정해진다

**허용되는 오차**: 실적 발표 직후 종목이 최대 10주간 이전 분기 숫자로 평가될 수 있다. 이 툴의 용도가 1~3년 보유 후보 리스트업이므로 감수 가능한 수준으로 판단한다. 단타·모멘텀 용도로 전환할 경우 이 설계를 재검토해야 한다.

## 4. 필터 동작 변경

`src/analyzers/trap_filter.py` 및 호출부:

- **필터는 야후를 직접 호출하지 않는다.** 입력을 전부 `fundamentals_cache`에서 읽는다.
- 캐시에 데이터가 없거나 Piotroski 계산에 필요한 3개년이 확보되지 않은 종목은 **탈락이 아니라 `데이터부족`으로 분류**한다.

### 결과 분류를 3가지로
현재 통과/탈락 2분류를 다음으로 확장한다:

```
통과 (pass) / 탈락 (fail) / 데이터부족 (insufficient_data)
```

이유: 상장 3년 미만, 회계연도 변경, 스핀오프 직후 기업은 F-Score가 낮은 게 아니라 **계산이 불가능**한 것이다. 없는 값을 0점으로 처리하면 이런 기업이 조용히 탈락한다. 하필 성장 초기 기업이 여기 몰릴 가능성이 높다.

실행 로그와 텔레그램 주간 요약에 세 숫자를 모두 출력한다:
```
유니버스 573 → 통과 161 / 탈락 380 / 데이터부족 32
```

## 5. 초기 백필 (별도 워크플로)

**주간 워크플로가 백필을 겸하게 하면 안 된다.** 캐시가 빈 첫 실행은 573종목 전체를 받아야 하고, 그게 정확히 지금 실패하는 그 실행이다.

`.github/workflows/backfill-fundamentals.yml` 신규 생성:

- 트리거: `workflow_dispatch` 전용 (스케줄 없음)
- 입력: `offset` (정수), `limit` (정수, 기본 50), `market` (`US`/`KR`/`ALL`)
- 동작: 유니버스를 티커 사전순 고정 정렬 → `offset`부터 `limit`개만 수집 → `fundamentals_cache`, `fetch_status` 갱신
- **배치 단위로 즉시 커밋한다.** 종목 하나 받을 때마다 저장해서, 중간에 실패해도 앞서 받은 것은 남는다.
- 종료 시 요약 출력: `처리 N / 성공 N / rate_limited N / no_data N`

**운영 방법**: `offset=0 limit=50` → `offset=50 limit=50` → ... 형태로 사람이 수동 실행. 하루 2~3회씩 2~3일에 나눠 진행. rate limit을 맞으면 그 배치만 실패하므로 잠시 뒤 같은 offset으로 재실행하면 된다.

## 6. 실패 내성

### 6.1 rate limit 재시도
`YFRateLimitError`를 명시적으로 잡아 지수 백오프로 재시도한다. 대기 시간은 60초 → 180초 → 600초, 최대 3회. 3회 실패 시 해당 종목을 `rate_limited`로 기록하고 다음 종목으로 넘어간다.

### 6.2 호출 사이 딜레이
종목 간 sleep을 넣는다 (기본 1.0초, 환경변수로 조정 가능).

근거: 현재 실행 시간은 11~19분이고 GitHub Actions 한도는 6시간이다. **시간 예산이 압도적으로 남으므로 속도를 팔아 안정성을 산다.** 40분이 걸려도 문제없다.

### 6.3 job이 죽지 않게
```
야후 호출 실패 → 캐시 있으면 캐시 사용 + 경고 로그
              → 캐시 없으면 해당 종목만 insufficient_data
              → 전체 job은 성공(exit 0)으로 종료
```

캐시 적중률이 임계치(예: 70%) 아래로 떨어진 경우에만 텔레그램 경고를 보낸다. job 실패로 처리하지는 않는다.

## 7. 시가총액 처리

유니버스 선별(미국 $2B+, 한국 2000억원+)에는 여전히 최신 시가총액이 필요하다. 이것만 매주 갱신 대상이다.

- **시가총액 = 주가 × 발행주식수**
- 발행주식수는 재무제표(balance) 항목이므로 캐시 대상이다
- 주가는 `yf.download()` 등으로 **다수 티커를 배치 호출**한다 (배치 크기 기본 100)

이렇게 하면 573회 개별 호출이 배치 몇 회로 줄어든다.

주의: 배치 호출도 rate limit 대상이다. 6.1의 재시도를 동일하게 적용하고, 실패 시 직전 주 시가총액으로 대체한 뒤 로그를 남긴다.

## 8. 워크플로 분리 (매수 단계 결합 해제)

`weekly-analysis.yml`에서 장기 포트폴리오(1y/3y) 매수는 일요일에 이미 저장된 `watchlist_candidates`를 읽어 실행된다. 따라서 **야후 조회가 실패해도 매수는 실행 가능해야 한다.**

- 매수 스텝을 수집·분석 스텝과 분리하고, 앞 스텝 실패와 무관하게 실행되도록 한다
- 매수에 시세가 필요한 경우 캐시된 직전 종가로 대체 가능하게 하고, 사용한 가격의 기준일을 기록한다
